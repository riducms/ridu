# Ridu shadcn Rhea component playground

This directory is Ridu's intake and evaluation playground for components generated from the
shadcn-svelte Rhea registry. It keeps a broad set of plausible UI primitives available so the real
admin can assess an existing implementation before inventing or installing one under feature
pressure.

It is intentionally isolated under `playground/` and may receive new candidate components. That is
its only active role.

## What this is for

- Add shadcn-svelte Rhea components that Ridu may plausibly need.
- Run and inspect them in a small Svelte 5 application.
- Understand their markup, Bits UI behavior, variants, dependencies, keyboard interaction, and
  accessibility before deciding whether to adopt them.
- Preserve upstream-oriented examples as useful comparison material during an intentional Ridu
  port.

Adding a component here records a candidate, not an architectural decision or production
dependency.

## What this is not

- It is not the framework-owned admin in `../../admin/`.
- It is not a template generated by the Ridu CLI.
- It is not part of the root Bun workspace or default verification commands.
- It is not a package that production code may import.
- It is not a reason to bulk-copy every shadcn component into Ridu.

Application and plugin scaffolds emitted by Ridu commands have separate framework-owned sources.
This playground has no relationship to that generated-project contract.

## Intentional differences from the Ridu admin

This playground stays close to shadcn-svelte's expected environment so registry components remain
easy to add and compare. It can retain:

- Tailwind CSS and registry-generated Tailwind utilities;
- `@lucide/svelte` component imports;
- shadcn registry aliases and generated file organization;
- dependencies used only by candidate components;
- upstream token and variant choices.

The real Ridu admin instead uses UnoCSS, semantic Ridu theme tokens, `unplugin-icons` virtual icon
imports, strict component ownership, and only the dependencies justified by shipped features.

## Promoting a component into Ridu

Promotion is an adaptation, not a file move:

1. Start from an actual admin feature and identify the smallest coherent primitive it needs.
2. Evaluate the candidate here, including keyboard, focus, controlled state, snippets, bindings,
   RTL, reduced motion, and accessible naming.
3. Copy only that primitive into the clean admin or its owning feature.
4. Replace `@lucide/svelte` imports with `~icons/lucide/*` imports.
5. Translate Tailwind-specific presentation to Ridu's UnoCSS utilities and semantic tokens.
6. Reconcile the current Svelte and Bits UI APIs rather than preserving generated code blindly.
7. Retain `tailwind-variants` contracts only where they improve the resulting Ridu API, and remove
   unused dependencies and variants.
8. Verify the adapted primitive inside the real admin with its focused checks.

The playground version may continue to exist after promotion so future registry updates can be
compared. The production component is owned and evolved by Ridu from that point onward.

## Playground commands

Run commands from this directory:

```sh
bun install
bun run dev
bun run check
bun run build
```

Use the shadcn-svelte CLI and the local `components.json` when adding registry candidates. Keep
playground-only package and configuration changes contained in this directory.
